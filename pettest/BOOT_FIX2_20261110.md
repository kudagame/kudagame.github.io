# 寵物 staging 修復第二輪（2026-11-10，Asia/Taipei）

## 這次找到的實際問題

上一輪的「8 秒 image timeout」會從大量請求排隊前就開始計時，逾時後清掉 onload 並把 A.imgs 設為 null。即使圖片稍後成功下載，也永遠不再採用。A.frame 又可能快取完全空白的 canvas。這會造成院子／戰鬥／頭像一直看不見，而不是素材檔全部不存在。

原版啟動一次請求 1369 個圖片 URL；所有物種、位階、動作、頭像及非院子場景都一起請求，並用時間戳阻止 HTTP cache重用。這使排隊更嚴重。現在 boot 不等網路圖片，僅依 manifest建立metadata；第一次新檔夜間院子穩態測得3張圖片（西施NPC idle、櫃檯頭像、夜院背景）。場景／頭像／圖紙按可見需求才請求，共用同URL的Image，最多6個併發。15秒時只釋放佇列，不刪除onload，遲到成功仍採用／清空相關快取。真正HTTP錯誤允許後續按需再試最多2次。尚未成功的身體不快取空白canvas。

## 舊anchors URL、SW與DEV

全部pet／dev／manifest／HTML掃描：沒有任何 ../chars、絕對URL、_stage1110字串或serviceWorker/cache程式。頁面不註冊SW，也不清除使用者現有SW。curl確認當時/_stagep/pet_art.js與第一輪修復本地檔相同，不會發出開發anchors請求。

主網站根SW只排除/pettest/，未排除/_stagep/或舊/_stage1110/；已裝主遊戲SW的瀏覽器可能對staging導航回舊首頁。不能從已刪舊staging重建當時情況，也不能把這判成確定原因。本任務只允許改_stagep，故沒有動根SW、沒有清使用者快取。仍需父代理用受支援瀏覽器確認實際頁面及控制器來源。
